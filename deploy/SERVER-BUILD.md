# فرستادن نسخه‌ی تازه به سرور: ساخت روی خود سرور

این سند توضیح می‌دهد که `./ship.sh` چطور کدی را که روی سیستم توسعه تست و push کرده‌اید، روی سرور می‌سازد و اجرا می‌کند.

---

## چرا ساخت روی سرور

| | فرستادن ایمیج از سیستم توسعه | ساخت روی سرور (روش فعلی) |
|---|---|---|
| حجم فرستادنی | ایمیج‌ها حدود ۴٫۵ گیگابایت | فقط شماره‌ی commitها |
| با آپلود فعلی (حدود ۰٫۲ مگابایت در ثانیه) | بار اول حدود ۷ ساعت؛ هر تغییر بسته‌های npm بیش از ۱ ساعت | هر نسخه چند دقیقه ساخت روی سرور |
| دسترسی سرور | — | GitHub، npm، دبیان و Docker Hub را مستقیم و سریع می‌گیرد |

**سرور فقط کدی را می‌سازد که push کرده‌اید.** جای کدنویسی نیست. کد روی سیستم توسعه نوشته و تست می‌شود، بعد همان commit روی سرور ساخته می‌شود. نسخه‌ی Node در Dockerfile و نسخه‌ی بسته‌ها در `package-lock.json` ثابت‌اند، پس نتیجه همان چیزی است که اینجا تست کرده‌اید.

---

## روند کار

```
سیستم توسعه                                              GitHub              سرور
───────────                                              ──────              ────
۱. کد را تغییر می‌دهید
۲. ./release.sh                 (ساخت ایمیج اینجا)
   docker compose up -d         (اجرا و تست اینجا)
۳. تأیید ← git commit ← git push  ─────────────────────►  commitها
۴. ./ship.sh deploy@79.127.99.134
      │  بررسی: چیزی commitنشده/pushنشده نباشد
      │  فایل‌های deploy/ ──────────────────────────────────────────────►  /opt/trabot/deploy
      └─ دستور ساخت ────────────────────────────────────────────────────►  git: همان commitها از GitHub
                                                                           docker compose build
                                                                           TAG در .env ← up ← migrations
```

## روش استفاده

### فرستادن نسخه‌ی تازه

```bash
cd ~/Transport/transport_backend/deploy
./ship.sh deploy@79.127.99.134
```

اولین بار ساخت حدود ۱۰ تا ۱۵ دقیقه طول می‌کشد. بعد از آن، به خاطر cache لایه‌ها، معمولاً چند دقیقه.

### برگشت به نسخه‌ی قبل

```bash
./ship.sh deploy@79.127.99.134 20261031-1405-3178122
```

- نسخه‌ای که قبلاً روی سرور ساخته شده، فقط **دوباره اجرا** می‌شود و چیزی ساخته نمی‌شود.
- فهرست نسخه‌های موجود روی سرور:
  ```bash
  ssh -i ~/.ssh/id_ed25519_vps deploy@79.127.99.134 "docker images 'trabot/transport' --format '{{.Tag}}  {{.CreatedSince}}'"
  ```
- اگر نسخه‌ی تازه **migration** داشته، برگرداندن کد دیتابیس را برنمی‌گرداند. پس قبل از فرستادن چنین نسخه‌ای، روی سرور یک پشتیبان بگیرید: `docker compose exec backup /backup.sh now`.

## `ship.sh` قدم‌به‌قدم چه می‌کند

### ۱. بررسی کد روی سیستم توسعه

برای هر سه پروژه (`transport_backend`، `trabari -backend`، `transport_front`):

| بررسی | اگر نباشد |
|---|---|
| هیچ فایل commitنشده‌ای (از فایل‌هایی که در git هستند) نمانده باشد | می‌ایستد: «commit and push them first» |
| commit فعلی روی GitHub باشد | می‌ایستد: «is not on GitHub yet: git push» |

فایل‌هایی که در git نیستند، مثل نمونه‌های صوتی یا تست‌های commitنشده، مانع نمی‌شوند. روی سرور هم نمی‌روند.

مسیر پروژه‌ها از `deploy/.env` همین سیستم خوانده می‌شود (`TRANSPORT_SRC`، `TARABARI_SRC`، `FRONT_SRC`).

**شماره‌ی نسخه** این‌طور ساخته می‌شود: تاریخ و ساعت + ۷ حرف اول commit پروژه‌ی Transport، مثلاً `20261031-1405-3178122`.

### ۲. فرستادن فایل‌های `deploy/`

compose، Caddyfile، اسکریپت‌ها و راهنماها با `rsync` به `/opt/trabot/deploy` می‌روند. **این‌ها هرگز فرستاده نمی‌شوند** و فقط روی خود سرورند:
- `.env`
- `config/` (توکن‌ها و کلیدها)
- `data/` (اطلاعات)
- کانفیگ VPN

### ۳. ساخت و اجرا روی سرور

1. **گرفتن کد:** هر پروژه در `/opt/trabot/src/` گرفته می‌شود و **دقیقاً روی همان commit** قرار می‌گیرد. بار اول `git clone` و بعد از آن `git fetch`.
   ```
   /opt/trabot/
     deploy/                  فایل‌های compose و تنظیمات سرور
     src/transport_backend/   کد، روی commit فرستاده‌شده
     src/tarabari_backend/
     src/transport_front/
   ```
2. **مسیر کدها در `.env` سرور:** `TRANSPORT_SRC`، `TARABARI_SRC` و `FRONT_SRC` خودکار به همین پوشه‌ها تنظیم می‌شوند.
3. **ساخت ایمیج‌ها:** `docker compose build transport tarabari web` با همان Dockerfileها. آینه‌های npm و دبیان از `NPM_REGISTRY` و `DEBIAN_MIRROR` در `.env` سرور خوانده می‌شوند.
4. **اجرا:** `TAG` در `.env` سرور روی نسخه‌ی تازه می‌رود و `docker compose up -d` سرویس‌های عوض‌شده را با نسخه‌ی جدید جایگزین می‌کند. چند ثانیه وقفه دارد.
5. **migrationهای** هر دو بک‌اند اجرا می‌شوند.
6. وضعیت سرویس‌ها نشان داده می‌شود (`docker compose ps`).

## چیزهایی که باید بدانید

- **مخزن‌ها روی GitHub عمومی‌اند،** پس سرور برای گرفتن کد اجازه‌ی خاصی لازم ندارد. اگر خصوصی شوند، باید روی سرور یک «Deploy key» فقط‌خواندنی برای هر مخزن اضافه کنیم.
- **فایل محرمانه هرگز در git نباشد.** چون سرور کد را از GitHub می‌گیرد، هر چه در git است عملاً عمومی است. توکن‌ها در `config/` سرور، و کلیدها در `config/*-keys` می‌مانند.
- **`cdn` (قالب‌ها و تصاویری که بک‌اندها نشان می‌دهند) در git نیست** و در ایمیج هم نیست. روی سرور در `data/transport/cdn` و `data/tarabari/cdn` است و یک بار با `rsync` منتقل می‌شود (`DEPLOYMENT.md` بخش ۵.۷).
- **فضای دیسک:** ایمیج‌های نسخه‌های قبلی روی سرور می‌مانند تا برگشت ممکن باشد. هر چند وقت یک بار نسخه‌های خیلی قدیمی را پاک کنید:
  ```bash
  docker image prune -a --filter "until=720h"     # ایمیج‌های بی‌استفاده‌ی قدیمی‌تر از ۳۰ روز
  ```
- **ساخت روی سیستم توسعه همچنان لازم است.** `./release.sh` و `docker compose up -d` برای تست قبل از push‌اند.

## عیب‌یابی

| پیام یا مشکل | علت | راه حل |
|---|---|---|
| `has uncommitted changes` | فایلی که در git است تغییر کرده و commit نشده | commit و push، یا `git stash` |
| `is not on GitHub yet` | commit شده ولی push نشده | `git push` |
| ساخت روی سرور سر `npm ci` یا `apt-get` گیر می‌کند | npm یا دبیان از سرور در دسترس نیست | `NPM_REGISTRY` یا `DEBIAN_MIRROR` در `.env` سرور را روی آینه‌ی ایرانی بگذارید |
| `the server has no images of …` (برگشت) | آن نسخه روی سرور ساخته نشده یا پاک شده | از فهرست نسخه‌های موجود یکی را انتخاب کنید |
| بعد از اجرا یک سرویس مدام ری‌استارت می‌شود | خطای برنامه یا تنظیم | `docker compose logs transport` و `data/transport/logs/error-*.log`؛ بعد برگشت به نسخه‌ی قبل |
