# Setas Backend

Backend پروژه Setas با **NestJS**، **TypeScript**، **PostgreSQL** و **TypeORM**.

این سرویس شامل ماژول‌های مختلفی مثل احراز هویت، مدیریت کاربران، انبار، منابع انسانی، آموزش، گزارش‌ها، نوتیفیکیشن و بخش Agent است.

## پیش‌نیازها

- Node.js 20 یا بالاتر
- npm 10 یا بالاتر
- PostgreSQL 14 یا بالاتر

## نصب

```bash
npm install
```

## تنظیمات محیطی

فایل `.env` باید در ریشه پروژه وجود داشته باشد. پروژه از `ConfigModule` برای خواندن تنظیمات استفاده می‌کند.

نمونه متغیرهای مهم:

```env
NODE_ENV=development
PORT=3001

DB_HOST=localhost
DB_PORT=5432
DB_USERNAME=postgres
DB_PASSWORD=your_password
DB_DATABASE=Setas
DB_SYNCHRONIZE=false

JWT_SECRET_KEY=your_jwt_secret
JWT_EXPIRATION_TIME=64800s

CORS_ORIGIN=http://localhost:3000,http://localhost:5173
CORS_METHODS=GET,HEAD,PUT,PATCH,POST,DELETE
CORS_CREDENTIALS=true

GOOGLE_CLIENT_ID=your_google_client_id
GOOGLE_CLIENT_SECRET=your_google_client_secret
GOOGLE_REDIRECT_URI=http://localhost:3001/api/auth/google/callback
API_MAIN_URL=http://localhost:3001/
```

نکته:

- مقدارهای واقعی را با اطلاعات محیط خودتان جایگزین کنید.
- `CORS_ORIGIN` می‌تواند چند دامنه با کاما جدا شود.
- این پروژه به PostgreSQL متصل می‌شود و با `synchronize=false` طراحی شده است، پس برای محیط واقعی بهتر است migrationها را مدیریت کنید.

## Seed

seed نقش‌ها فقط با دستور زیر اجرا می‌شود و هنگام راه‌اندازی برنامه اجرای خودکار ندارد:

```bash
npm run seed
```

این دستور با تنظیمات دیتابیس `.env`، جدول `Role` را بررسی می‌کند. فقط اگر جدول خالی باشد،
نقش‌های `DRIVER`، `COMPANY`، `BROKER` (از `AccountType`) و `ADMIN` را با وضعیت فعال و عنوان‌های فارسی «راننده»، «شرکت»، «واسطه» و «مدیر سیستم» درج می‌کند.
اگر حتی یک نقش موجود باشد، هیچ تغییری اعمال نمی‌شود. سپس کاربر `super_admin` را در صورت نبودن با رمز هش‌شده ایجاد و نقش `ADMIN` را به آن متصل می‌کند. نقش `ADMIN` و اتصال آن نیز در صورت نبودن ایجاد می‌شوند؛ رمز کاربر موجود تغییر نمی‌کند.

## ثبت‌نام با OTP

مسیر ثبت‌نام مستقیم `/api/auth/register` با دو مرحله زیر جایگزین شده است.

```http
POST /api/auth/register/request-otp
Content-Type: application/json
```

```json
{
  "username": "new_user",
  "password": "MyPassword123",
  "phoneNumber": "09123456789",
  "accountType": "DRIVER"
}
```

نوع حساب یکی از `DRIVER`، `COMPANY` یا `BROKER` است. شماره‌های ایرانی به قالب `09…`
تبدیل می‌شوند. پاسخ موفق HTTP 200 شامل `phoneNumber`، `expiresIn: 300` و `retryAfter: 60`
در فیلد `data` است. رمز قبل از ذخیره موقت هش می‌شود؛ کد OTP در پاسخ یا لاگ برگردانده نمی‌شود.

```http
POST /api/auth/register/verify-otp
Content-Type: application/json
```

```json
{ "phoneNumber": "09123456789", "code": "123456" }
```

کد باید رشته شش‌رقمی باشد. بعد از پنج تلاش اشتباه باید کد جدید درخواست شود.
پس از تأیید، نام کاربری و شماره دوباره بررسی و کاربر همراه نقش فعال ساخته می‌شود.
نقش باید قبلاً در دیتابیس وجود داشته باشد (`npm run seed`). پاسخ HTTP 201 در `data`
شامل `accessToken`، `refreshToken` و `tokenType: "Bearer"` است.

```http
POST /api/auth/refresh
Content-Type: application/json
```

```json
{ "refreshToken": "<refreshToken returned by verify-otp>" }
```

refresh token سی‌روزه و یک‌بارمصرف است؛ پاسخ شامل یک جفت توکن جدید است.
access token با تنظیمات JWT فعلی صادر می‌شود. refresh token فقط در این مسیر قابل استفاده است.
در صورت خطای زیرساخت پس از ساخت حساب، ممکن است حساب ساخته شده باشد ولی پاسخ توکن نرسد؛
در این حالت کاربر می‌تواند از مسیر لاگین موجود استفاده کند.

**اتصال پیامک ملی‌پیامک:** در فایل `.env` توکن بخش «وب‌سرویس‌ها ← ارسال پیامک ← رمز یکبار مصرف»
کنسول ملی‌پیامک را تنظیم کنید و برنامه را دوباره اجرا کنید:

```dotenv
MELIPAYAMAK_OTP_TOKEN=your-console-otp-token
```

ارسال با HTTPS و متد `POST https://console.melipayamak.com/api/send/otp/<TOKEN>` و بدنه JSON
`{ "to": "<موبایل>" }` انجام می‌شود. کد را خود ملی‌پیامک می‌سازد و در `code` پاسخ برمی‌گرداند؛
برنامه فقط HMAC آن را در Redis نگه می‌دارد. پر بودن `status` در پاسخ به معنی خطاست.
الگو یا شماره خط ارسال لازم نیست. طول کد را ملی‌پیامک تعیین می‌کند (۴ تا ۱۰ رقم پذیرفته می‌شود).

مهلت پاسخ سرویس ۱۰ ثانیه است. تنظیمات ناقص، خطای شبکه یا رد درخواست توسط ملی‌پیامک
به خطای 503 تبدیل می‌شود و اطلاعات ثبت‌نام موقت و محدودیت ارسال مجدد از Redis پاک می‌شوند.
کلید API، کد و جزئیات خام خطای سرویس در پاسخ یا لاگ ثبت نمی‌شوند.
Redis و PostgreSQL نیز باید در دسترس باشند. تست‌های خودکار پیامک واقعی ارسال نمی‌کنند.

## شناسایی و ثبت‌نام تلگرام

قبل از پردازش پیام یا callback در چت خصوصی، `TelegramAccessService` شناسایی را انجام می‌دهد:

1. `TelegramIdentityService.getUserId` ابتدا کلید `telegram:identity:v1:<botId>:<telegramUserId>` را از Redis می‌خواند. مقدار آن فقط `userId` است و در صورت وجود، شناسایی بدون Query به PostgreSQL انجام می‌شود.
2. در Cache Miss، `TelegramLink` خوانده و اتصال موجود برای ۲۴ ساعت Cache می‌شود. برای کاربران ناشناس رکورد اتصال ایجاد نمی‌شود؛ لینک قدیمی با `userId` خالی نیز ناشناس محسوب می‌شود.
3. کاربر ناشناس دکمه «📱 ارسال شماره موبایل من» را می‌بیند. فقط Contact با `contact.user_id === from.id` پذیرفته می‌شود؛ شماره متنی یا Contact شخص دیگر پذیرفته نیست. مطابق [Telegram Bot API](https://core.telegram.org/bots/api#keyboardbutton)، درخواست Contact در چت خصوصی انجام می‌شود.
4. شماره ایرانی Normalize می‌شود. حساب موجود با همان شماره، بدون تغییر رمز یا نقش به تلگرام متصل می‌شود. حساب غیرفعال یا حساب متصل به تلگرام دیگر پذیرفته نمی‌شود.
5. برای شماره جدید، ابتدا User بدون نقش و TelegramLink در یک تراکنش PostgreSQL ساخته می‌شوند. نام کاربری شماره موبایل Normalize‌شده است؛ رمز تصادفی تولید و فقط هش آن ذخیره می‌شود. مشخصات ورود وب در چت خصوصی ارسال و هویت Cache می‌شود.
6. سپس دکمه‌های `DRIVER / COMPANY / BROKER` برای تکمیل همان حساب نمایش داده می‌شوند. انتخاب نوع، UserRole را به حساب موجود اضافه می‌کند؛ حساب و رمز دوباره ساخته نمی‌شوند. نقش فعال باید از قبل موجود باشد (`npm run seed`). قفل سطری دیتابیس جلوی تخصیص چند نقش از کلیک‌های هم‌زمان را می‌گیرد.
7. اگر کاربر انتخاب نوع را رها کند، با مراجعه بعدی از روی نبود نقش دوباره به این مرحله هدایت می‌شود؛ وابسته به باقی‌ماندن Session نیست. ورود وب تا انتخاب نقش، طبق اعتبارسنجی فعلی ورود مجاز نیست.


کلیدها در `redis.keys.ts` تعریف شده‌اند. قفل Redis از اجرای هم‌زمان ثبت‌نام برای یک کاربر و Bot جلوگیری می‌کند؛ محدودیت‌های یکتایی دیتابیس نیز برقرارند. نقش‌های لازم برای نمایش منو جداگانه برای ۲۴ ساعت Cache می‌شوند؛ این Cache مجوز انجام عملیات نیست.

Redis و PostgreSQL باید در دسترس باشند. تغییر جدول یا migration جدید لازم نیست. ساخت حساب اولیه اشتراک فعال ایجاد نمی‌کند؛ فرایند قدیمی تأیید خرید و ساخت حساب پس از پرداخت در این تغییر بازنویسی نشده است و برای حساب‌های ازقبل‌ساخته‌شده به تطبیق جداگانه نیاز دارد.

ارسال پیام تلگرام و تراکنش دیتابیس اتمیک نیستند: اگر ارسال مشخصات ورود بعد از ساخت حساب شکست بخورد، حساب و اتصال باقی می‌مانند و رمز خام برای ارسال مجدد ذخیره نمی‌شود؛ بازیابی دسترسی وب در این حالت نیازمند پشتیبانی است. تست‌های این جریان با سرویس‌های شبیه‌سازی‌شده اجرا می‌شوند و پیام واقعی ارسال نمی‌کنند.

### نمایش طرح‌ها پیش از منوی تلگرام

پس از تکمیل حساب و در مراجعه‌های بعدی، `TelegramSubscriptionService` اشتراک کاربر را بررسی می‌کند.
اشتراک معتبر باید `Active` باشد و `startAt <= now < expireAt` برقرار باشد. این بررسی از دیتابیس
انجام می‌شود تا انقضا و فعال‌شدن اشتراک در مراجعه بعدی اعمال شوند.
اگر اشتراک معتبر وجود نداشته باشد، منوی عملیات نمایش داده نمی‌شود؛ طرح‌های فعال نقش کاربر
با عنوان «یکی از طرح‌ها را انتخاب کنید» و دکمه‌های انتخاب طرح نمایش داده می‌شوند.
در نبود طرح فعال، پیام مربوط همراه دکمه پشتیبانی نمایش داده می‌شود.
انتخاب طرح به مسیر فعلی خرید متصل است؛ ارسال رسید و پیگیری پرداخت مسدود نمی‌شوند.
این تغییر نمایش منو و دسترسی به عملیات تلگرام را کنترل می‌کند؛ محدودیت فرایند قدیمی
تأیید خرید برای حساب‌های ازقبل‌ساخته‌شده که بالاتر توضیح داده شده، همچنان برقرار است.
